# RB-08 ↔ rb-llm JSON protocol (`rb-llm/1`)

This is the contract between **RB-08** (rbvoice, the client) and **rb-llm** (the server). The JSON Schemas in [`schemas/`](../schemas/) are normative. This page explains them. Request/response examples are in [`examples/`](../examples/).

## Transport

- HTTP/1.1, JSON bodies, UTF-8 (`Content-Type: application/json`). Accented words are sent as is, as rbvoice does for Vosk.
- Default address: `http://rb-llm.local:8091` (configurable). All routes are under `/v1`.
- No authentication in v1. The service binds to the avionics LAN only and must never be exposed beyond it. An optional shared token (`Authorization: Bearer …`) is reserved for v1.x.
- Keep-alive is recommended: RB-08 keeps one persistent connection.

## Endpoints

| Method and path | Purpose | Schema |
|---|---|---|
| `GET /v1/health` | Liveness and readiness, thermal state | `health.schema.json#/$defs/health` |
| `GET /v1/info` | Version, supported protocols, tasks, languages, models | `health.schema.json#/$defs/info` |
| `PUT /v1/catalog` | Upload the active rbvoice case file, get `catalog_hash` | `catalog.schema.json` |
| `GET /v1/catalog/{lang}` | Current hash and stats for a language | `catalog.schema.json#/$defs/put_response` |
| `POST /v1/parse` | Parse one utterance (command, ATC or auto) | `parse-request` / `parse-response` |
| `POST /v1/ask` | Answer a question from the aircraft status | `ask-request` / `ask-response` |
| `GET /v1/status` | Facts the model would see (`?source=auto\|rb\|demo`, `&raw=1` for the raw snapshot) | — (debug / web UI) |
| `POST /v1/status` | Facts for a posted RB-01 snapshot | — (debug / web UI) |
| `GET /` | Web console | — |

There is a single parse endpoint. The task is a field, so the client does not need to know in advance whether an utterance is a command or ATC (`task: "auto"`).

## Conventions

| Item | Rule |
|---|---|
| Versioning | `protocol: "rb-llm/1"` in every body. Minor versions (`rb-llm/1.1`) only **add** optional fields or enum values. Clients must ignore unknown fields, and must treat an unknown `instruction.type` like `unparsed`. A breaking change becomes `/v2`. |
| Ids | `request_id` is generated by the client (UUID) and echoed back. `session_id` is stable for one RB-08 run. |
| Identifiers | `component` and `parameter` are rbvoice case-file identifiers (keyword values / endpoint keys). They are not translated. |
| Frequencies | String, three decimals: `"118.500"` |
| Altitude | Integer feet with `"unit":"ft"`, or integer flight level with `"unit":"FL"` |
| Heading / wind direction | Integer degrees, 1–360 (0 allowed for calm wind) |
| QNH | Integer hPa (`"unit":"hPa"`), or a decimal with `"unit":"inHg"` |
| Squawk | String of 4 octal digits |
| Durations | Integer seconds |
| Nulls | Optional objects may be `null` or absent. Both mean "not applicable". |

## `POST /v1/parse`

### Request

```json
{
  "protocol": "rb-llm/1",
  "request_id": "5d0c6a52-2a7e-4c2f-9d0e-0e2f3b1c9a10",
  "session_id": "rb08-20261125-0812",
  "task": "auto",
  "lang": "it",
  "text": "computer dimmi le temperature dei cilindri",
  "alternatives": [{ "text": "computer dimmi le temperature dei cilindro", "confidence": 0.41 }],
  "stt": { "engine": "vosk", "model": "vosk-model-it-0.22", "confidence": 0.86 },
  "source": "intercom",
  "catalog_hash": "9f2c1e7a3b4d5e6f",
  "context": {
    "wake_word": "computer",
    "target": "computer",
    "own_callsign": { "registration": "I-ABCD", "spoken": ["india alfa bravo charlie delta", "india charlie delta"] },
    "session": { "last_action": "GET", "last_component": "situation", "last_parameter": "GPSAltitudeMSL" },
    "radio": { "active_mhz": "122.500", "standby_mhz": "118.100" }
  },
  "options": { "deadline_ms": 2500 }
}
```

Only `protocol`, `request_id`, `lang` and `text` are required. The more context RB-08 sends, the better the results:

- `context.wake_word` / `source: "push_to_talk"`: the utterance is surely for the RB, so classification is skipped.
- `context.session`: enables follow-ups ("e il secondo?").
- `context.own_callsign`: required for useful ATC results (`addressee`, readback).
- `context.stations` / `context.airfields`: short nearby lists (≤ 20) help the LLM spell names that it will hear on the radio. RB-08 still resolves names against its own databases.
- `context.last_clearance`: send it with a pilot's readback to get a `readback_check`.

### Response: command

```json
{
  "protocol": "rb-llm/1",
  "request_id": "5d0c6a52-2a7e-4c2f-9d0e-0e2f3b1c9a10",
  "status": "ok",
  "kind": "command",
  "addressee": "rb",
  "confidence": 0.94,
  "normalized_text": "temperature cilindri",
  "command": {
    "action": "GET",
    "component": "ems",
    "parameter": "cht",
    "target": "computer",
    "args": {},
    "from_context": false,
    "requires_confirmation": false,
    "evidence": "temperature cilindri"
  },
  "atc": null,
  "answer": null,
  "engine": { "path": "rules", "model": null, "latency_ms": 4 },
  "warnings": [],
  "error": null
}
```

RB-08 then runs exactly what its keyword matcher would have produced: for `ems/cht`, it calls the generic handler with `endpoints["cht"]`, applies `reply_template` and speaks the reply. rb-llm **does not** fetch values or write the spoken answer for commands. The only exception is `answer.speak` carrying a clarification question when `status` is `no_match` and a question is useful ("Quale serbatoio, uno o due?").

### Response: ATC

```json
{
  "protocol": "rb-llm/1",
  "request_id": "0b7e…",
  "status": "ok",
  "kind": "atc",
  "addressee": "own_aircraft",
  "confidence": 0.88,
  "normalized_text": "ICD perugia tower climb altitude 5000 ft qnh 1013",
  "command": null,
  "atc": {
    "callsign": { "heard": "india charlie delta", "match": "own", "score": 0.97 },
    "station": "perugia tower",
    "instructions": [
      { "type": "altitude", "verb": "climb", "value": 5000, "unit": "ft", "readback_required": true, "evidence": "climb altitude 5000 ft" },
      { "type": "qnh", "value": 1013, "unit": "hPa", "readback_required": true, "evidence": "qnh 1013" }
    ],
    "readback": { "required": true, "text": "Climb altitude 5000 feet, QNH 1013, India Charlie Delta", "lang": "en" },
    "suggested_actions": []
  },
  "answer": { "speak": null, "display": "ALT CLB 5000 FT · QNH 1013", "lang": "en" },
  "engine": { "path": "rules+llm", "model": "qwen3-4b-instruct-q4_k_m", "latency_ms": 1840 },
  "warnings": [],
  "error": null
}
```

A `frequency_change` instruction produces a **suggested action** (`radio/radio SET` with `frequency_mhz`, `requires_confirmation: true`). RB-08 may offer it to the pilot ("Set standby 118.100?"). It must never apply it on its own.

### Status semantics

| `status` | Meaning | RB-08 should |
|---|---|---|
| `ok` | `command` (kind `command`) or `atc` (kind `atc`/`readback`) is filled | Execute or show |
| `no_match` | Addressed to the RB, but no valid intent | Fall back to the keyword matcher; if that fails too, speak `answer.speak` or stay silent, as today |
| `not_addressed` | Not for the RB, and not ATC for us. `atc` may still hold traffic for other aircraft | Ignore, or log for situational awareness |
| `error` | See `error.code` | Fall back to the keyword matcher |

`no_match`, `not_addressed` and in-band errors use **HTTP 200**. HTTP error statuses are for transport and protocol problems:

| HTTP | `error.code` | When |
|---|---|---|
| 400 | `bad_request` | Body fails the schema (the response lists the first violations in `message`) |
| 409 | `catalog_mismatch` | `catalog_hash` is unknown. The client re-runs `PUT /v1/catalog` and retries once |
| 422 | `unsupported_lang` / `unsupported_task` | Language or task not enabled on this server |
| 503 | `loading` / `busy` | Model not loaded yet, or the queue is full. Includes `retry_after_ms` |
| 504 | `timeout` | The deadline expired before any result. Do not retry: fall back |
| 500 | `internal` / `engine_failure` | Bug or engine crash. The server degrades to rules-only |

Errors with an HTTP status still return a full response body (`status: "error"`, `kind: "unknown"`, `engine.path: "none"`), so the client has a single parsing path.

### Confidence and thresholds

`confidence` is calibrated on the evaluation set ([roadmap](roadmap.md)). It does not come from the model's self-report. Suggested client policy:

| Confidence | GET | SET / DEL |
|---|---|---|
| ≥ 0.85 | execute | execute |
| 0.6 – 0.85 | execute | ask for confirmation (rb-llm already sets `requires_confirmation`) |
| < 0.6 | rb-llm returns `no_match` | `no_match` |

## `POST /v1/ask`

This endpoint answers the pilot's question from the aircraft status. The status comes from `aircraft_status` in the request (an RB-01 snapshot keyed by endpoint, as in `data/demo-rb01.json`), or from the RB-01 that rb-llm reads itself (`--rb-url`), or from the demo snapshot.

```json
{ "protocol": "rb-llm/1", "request_id": "…", "lang": "en", "text": "where are we?",
  "options": { "deadline_ms": 12000, "status_source": "auto" } }
```

→

```json
{ "protocol": "rb-llm/1", "request_id": "…", "status": "ok", "kind": "ask",
  "answer": { "speak": "Latitude 43.10 north, longitude 12.25 east, 0.2 miles from Montemelino Airfield, bearing 135° true.", "lang": "en" },
  "facts_used": ["gps.position", "airfield.nearest_1"], "status_source": "demo",
  "engine": { "path": "llm", "model": "qwen3-1.7b", "latency_ms": 7925, "tokens_out": 52, "cached_tokens": 1020, "tok_per_s": 7.2 },
  "warnings": [], "error": null }
```

| `status` | Meaning | RB-08 should |
|---|---|---|
| `ok` | `answer.speak` is ready for TTS | speak it |
| `refused` | The model refused to use the data, even after one retry | not speak it; fall back or stay silent |
| `no_data` | No aircraft data reachable | speak the localized "not available" in `answer.speak`, or stay silent |
| `error` | See `error.code` | fall back |

`warnings` lists numbers in the answer that are not in the facts shown to the model (an "ungrounded" number). A client may refuse to speak an answer that has such a warning.

## Deadlines

If a request has no `options.deadline_ms`, the server uses `command` 4000 ms, `atc` 8000 ms and `ask` 12000 ms (`serve --deadline-ms` overrides all three). RB-08 should always send its own deadline. When it expires, generation is cancelled in the engine, so a late request never delays the next one.

## `PUT /v1/catalog`

```json
{
  "protocol": "rb-llm/1",
  "lang": "it",
  "source": "/boot/firmware/rb/rbvoice-cases.it.json",
  "case_file": { "language": "it", "components": { "…": "…" } }
}
```

→ `200 {"protocol":"rb-llm/1","lang":"it","catalog_hash":"9f2c1e7a3b4d5e6f","components":8,"parameters":62,"warnings":[]}`

RB-08 sends this once at startup, after `GET /v1/health` reports `ready`, and again whenever the case file changes or a 409 arrives. rb-llm regenerates the grammar and the static prompt for that language. The first parse after a catalog change is slower, because the KV cache is cold.

## `GET /v1/health`

```json
{ "status": "ready", "uptime_s": 5321, "models_loaded": ["qwen3-1.7b-instruct-q4_k_m"],
  "catalogs": { "it": "9f2c1e7a3b4d5e6f" }, "soc_temp_c": 61.2, "throttled": false, "queue_depth": 0 }
```

`degraded` means the LLM engine is down, and only the rules path answers. RB-08 polls this every 30 s and shows the state on the voice page (planned).

## Client checklist (RB-08)

1. At startup, poll `GET /v1/health` until `ready` or `degraded`. Do not block startup: the keyword matcher works without rb-llm.
2. `PUT /v1/catalog` with the active case file, and store `catalog_hash`.
3. For each utterance, `POST /v1/parse` with an HTTP timeout = `deadline_ms` + 300 ms.
4. Apply the status table above. **On any failure, fall back to the keyword matcher.** rb-llm must never make RB-08 worse than it is today.
5. Never execute an `atc.suggested_actions` item without explicit pilot confirmation.
